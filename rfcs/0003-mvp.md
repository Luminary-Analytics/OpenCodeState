# RFC 0003: MVP

Status: Draft

## Summary

This RFC defines the first local OpenCodeState prototype: a daemonless vertical
slice that takes a developer from `ocs init` through `ocs finish` to a structured,
reviewable package and a Git export — with no AI required.

The goal is not feature coverage. It is to make the manifesto *tangible* by
shipping the thinnest end-to-end spine, then thickening each segment. Everything
in later milestones (continuous capture, AI packaging, collaboration, semantic
integration) is an enhancement of this spine rather than a leap of faith.

## Scope

In scope for the MVP:

- `ocs init`, `ocs start`, `ocs checkpoint`, `ocs finish`, `ocs status`, `ocs log`, `ocs restore`, `ocs export`, `ocs run`
- Content-addressed snapshots and checkpoint restore (see [ocs-storage](../specs/ocs-storage.md), [ocs-checkpoints](../specs/ocs-checkpoints.md))
- Sessions with start/finish lifecycle (see [ocs-sessions](../specs/ocs-sessions.md))
- Heuristic (Tier-0) change-unit grouping, no AI (see [RFC 0004](0004-change-grouping.md))
- Package generation (see [ocs-packages](../specs/ocs-packages.md))
- Validation + risk evidence via a codebase-intelligence provider, with `fallow` first for TypeScript/JavaScript (see [RFC 0005](0005-codebase-intelligence-providers.md))
- Git export of a package to a branch

Explicitly out of scope for the MVP (deferred to later milestones):

- A continuous filesystem-watcher daemon (capture is hook-driven; see below)
- AI-based intent inference and hunk-level splitting (Tier-1)
- Collaboration server, registry, release lines
- Semantic / AST-aware integration and merge

## Implementation architecture

The reference implementation is a **hybrid**, mirroring the shape of tools like
`fallow` (a Rust core distributed through an npm/MCP surface):

- **Rust core** — the perf- and storage-sensitive engine: object model, content
  store (gitoxide-backed), session/checkpoint/package logic, the grouping
  pipeline, and the Git adapter. Distributed via an `npx` wrapper so it is
  invocable from JS and agent toolchains.
- **TypeScript surface** — the integration layer: CLI distribution, VS Code
  extension, MCP server, and the codebase-intelligence provider adapters. This
  surface is itself analyzed and gated by `fallow`.

This split keeps systems work in Rust where it is strongest, and keeps the
agent/IDE/analysis ecosystem in TypeScript where it is strongest.

## Storage

The MVP operates **inside an existing Git repository**. OpenCodeState reuses the
repository's object database for content, stores its own refs under
`refs/ocs/*`, and keeps session/package metadata in `.ocs/state.db` (SQLite).
Because content objects already live in the Git object store, `ocs export` is
near-free: it synthesizes ordinary commits and a branch from objects that are
already present. See [ocs-storage](../specs/ocs-storage.md).

## Capture model: daemonless, hook-driven checkpoints

The MVP does not run an always-on watcher. Instead, a **checkpoint is a cheap,
content-addressed, actor-tagged event**, fired by things that already happen:

- an explicit `ocs checkpoint`
- a wrapped command (`ocs run <cmd>`, e.g. tests)
- an editor save (via the VS Code extension)
- an agent edit (via a Claude Code hook → `ocs checkpoint --actor ai:<name>`)

This yields a *timeline*, *provenance* (per-checkpoint actor), and a *temporal
grouping signal* — all without a daemon. The continuous watcher is a later
optimization that simply fires the same checkpoint path automatically.

## Developer flow

```bash
ocs init     # register an OCS workspace inside the repo
ocs start    # open a session; record the baseline tree + HEAD
# ...code normally; checkpoints fire from hooks and `ocs run`...
ocs finish   # analyze the session and produce package(s)
```

`ocs finish` runs the pipeline:

1. Diff the baseline tree against the working tree; fold in the checkpoint timeline.
2. Group changes into change units (Tier-0 heuristics; [RFC 0004](0004-change-grouping.md)).
3. Run the codebase-intelligence provider to attach validation evidence and risk ([RFC 0005](0005-codebase-intelligence-providers.md)).
4. Decide:
   - **Clean and unambiguous** (one unit, no introduced error-level issues, high grouping confidence) → produce the package, optionally auto-export. Stay silent.
   - **Otherwise** (multiple units, introduced risk, a secret, or low confidence) → stop and present the plan for approve / edit / split / merge / reject.

That asymmetry — silent when clean, interrupting only when judgment is required —
is the product, expressed as one branch in one code path.

## Win condition

For the MVP to matter, `ocs finish` must beat `git commit` for a **single
developer**. It wins on exactly two things, and both must be excellent:

1. **The checkpoint safety net** — recover to any point in a session without
   having had the foresight to make a WIP commit.
2. **Automatic change-unit splitting** — turn a messy session into several
   clean, separately-reviewable packages with no manual hunk staging.

Everything else in the MVP is scaffolding for these two wins.

## North-star demo

> Spend a morning: fix a bug, bump a dependency, edit the README. Run `ocs
> finish`. It returns three clean packages — tests already run, the dependency
> change flagged — and you `ocs export` two to a branch and park the third. You
> never staged a hunk or wrote a commit message. Mid-session you `ocs restore`
> to undo a bad refactor without a stash.

Because the TypeScript surface is itself a TS/JS repo, OpenCodeState can manage
itself with `fallow` as the provider — the demo dogfoods.

## Build phases

- **Phase 1 — Vertical slice (this RFC):** the spine above, self-hosted.
- **Phase 2 — Continuous capture:** watcher daemon, auto-checkpoints, VS Code events.
- **Phase 3 — AI-assisted packaging:** Tier-1 intent/grouping, transcript provenance.
- **Phase 4 — Collaboration:** registry, review, release lines, host adapters.
- **Phase 5 — Provenance hardening + semantic integration.**

## Open questions

- What is the minimum useful checkpoint trigger set before the watcher exists?
- Should `ocs export` default to one commit per change unit, or one squashed commit per package?
- How should `ocs finish` behave when run repeatedly on an already-packaged session?
- Where is the default threshold for the "stay silent vs. interrupt" decision, before policy exists?
